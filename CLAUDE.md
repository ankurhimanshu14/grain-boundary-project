# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Analysis of SCADA temperature exports (Excel: `Date, Time, SET-1/PV-1 … SET-6/PV-6`) from a 3-zone continuous gas-fired pusher furnace (6 thermocouples, 2 per zone, named TC-01 … TC-06 in both apps: TC-01/TC-02 = Zone 1 …; **odd-numbered = right wall, even-numbered = left wall**; hardening chamber 13 tray positions split 5/4/4, tempering chamber 12 split 4/4/4; at every push the extractor takes the 13th tray out of the hardening chamber, a new tray is pushed in and, at the same time, the 26th tray is taken out of the tempering chamber; for isothermal annealing the extracted tray goes on a rail into the one-tray controlled cooling chamber, air is blown for the cooling time and it is then pushed into the tempering chamber, all within the same push cycle, so the cooling cycle (transfers + cooling) must end before the next push; the cooling chamber is not a line position: 13 + 1 + 12 = 26 trays right after a push; **measured** (push 18 min: first tray in 01:06, out of the hardening chamber 05:00 = 13 pushes, out of the tempering chamber 08:18 = 11 more pushes) a tray leaves the tempering chamber at the 11th push after leaving the hardening chamber, so it is in the furnace 24 push times — setting `tPush` = 11 on the production and specification pages), producing a CQI-9 style review and a printable report. `sample_data/` holds a real export.

## The three generations (only one is current)

- **`Pusher_Furnace_SCADA_Review.html` is the current app and the one the user iterates on.** One self-contained file (HTML + CSS + JS), edited directly: there is no build step and no bundler. It loads `xlsx.full.min.js` 0.18.5 and `Chart.js` 4.4.1 from cdnjs and works offline once those are cached; the page also embeds an example dataset (`SAMPLE`).
- `furnace_analyzer.html` (built from `standalone/src.html` with `python standalone/build.py`) and the Python/Streamlit app (`app.py`, `cqi9/`, `run_report.py`, `tests/`) are older, simpler versions. They do **not** have set-value changes, settling, hardening/tempering rules, furnace start/stop or the replacement register. Don't port new features to them unless asked. `README.md` describes only these older versions.

## CALOR, the main application (`CALOR.html`)

**CALOR** is the user's name for the main application (formerly "Heat Treat Quality Suite"; internal names such as the `HTQ` bridge, the `htq-theme` key and the `suite/` folder are kept). It combines the ten applications below into one file with a navigation bar ("Dashboard" | PRODUCTION: "Daily production" | PROCESS: "Specifications", "SCADA review", "Alarms", "Quench media" | QUALITY: "Hardness", "CP & PFMEA" | PYROMETRY: "SAT", "TUS", "Equipment", `#home` (default) / `#prod` / `#spec` / `#scada` / `#ops` / `#quench` / `#metal` / `#cpf` / `#sat` / `#tus` / `#equip`; keep tab names short — the bar must stay one row at 1366 px with every badge shown; short tab names, and the group labels (`.pd`) hidden below 1480 px, so the bar fits one row at 1366 px even with badges; below 1480 px the tabs also get tighter padding; "Start-up & alarms" was too long, hence "Alarms" with the full name as the tooltip; the bar wraps when narrow, the Data and Theme buttons sit in the header next to the document-control strip). **It is generated: never edit it.** Edit `Production_Report.html`, `Process_Specifications.html`, `Pusher_Furnace_SCADA_Review.html`, `Furnace_Operations.html`, `Quench_Media_Testing.html`, `Hardness_Metallurgical_Testing.html`, `Thermocouple_SAT_PDCA.html`, `Temperature_Uniformity_Survey.html`, `Equipment_Qualification.html`, `Control_Plan_PFMEA.html` or `suite/shell.html`, then run `python suite/build.py`; rebuild after every change to any app.

- **Look (the user's MWS MSA Manager style):** company line "Mass Wire and Steels Pvt. Ltd. · Bhiwadi" over the condensed CALOR heading, a boxed document-control strip (standard, scope, records, date), module tabs in labelled groups (Dashboard | PROCESS: SCADA temperature review | PYROMETRY: Thermocouple SAT) with the active tab dark-filled, Barlow Semi Condensed for headings and big figures with IBM Plex for text, a cool grey-green palette with teal-blue accent, large-figure tiles, a PLAN/DO/CHECK/ACT strip on the dashboard, tables with small uppercase headers, soft status pills and neutral outlined buttons. The shell styles itself; the pages get the same look from `suite/calor-theme.css`, which `suite/build.py` inserts into each page's `<head>` (plus the Barlow font) when it builds CALOR. The theme uses `:root`-prefixed selectors (tokens `:root:root:root`) so it overrides the page CSS regardless of order; it only restyles (tokens, type, chips → pills, tables, buttons, tiles, verdict), never changes layout or behaviour. The standalone page files keep their own look. When a page gets new components, add their restyle to `calor-theme.css`.
- `suite/build.py` embeds each app's HTML (with the theme added) as a JSON string in the shell; the shell loads them as `srcdoc` iframes. Same-origin frames, so both pages share `localStorage` and call each other through `window.HTQ` in the shell. Both apps stay fully usable as standalone files: each detects the suite with `const HTQ=window.parent.HTQ||null` and skips every suite feature when it is `null`.
- Bridge: `HTQ.provide(name, api)` / `HTQ.api(name)` (the SAT page provides `"sat"`, the SCADA page `"scada"`, the quench page `"quench"`, the specification page `"spec"`, the hardness page `"metal"`, the production page `"prod"`, the TUS page `"tus"`, the equipment page `"equip"`, the control plan / PFMEA page `"cpf"`, the start-up / alarm page `"ops"`), `HTQ.on/emit(event)` (`ops:changed`, `cpf:changed`, `equip:changed`, `tus:ready`, `tus:changed`, `prod:changed`, `spec:ready`, `spec:changed`, `metal:ready`, `metal:changed`, `sat:ready`, `sat:changed` (debounced from the SAT `save()`), `scada:ready`, `scada:changed`, `quench:ready`, `quench:changed`), `HTQ.go(page, opts)` (switches the tab and emits `nav:<page>`, e.g. `{view:{f,ch}}` or `{cycle}` for the SAT page).
- SCADA → SAT: the record is linked to a furnace and chamber of the SAT register (`link()`: `FURNACE-4` in the chart heading → `F-04`, `detectFurnace` → chamber; manual override per `furnaceKey` in `localStorage` `pfsr-link`). Replacements of that chamber from the SAT register join the SCADA analysis (`ALLREPL = REPL + satRepl()`; one without a time is `dayOnly` and judged on days only). `A.sat = satStatus(A)` drives the "Pyrometry status from the SAT register" section and `satObs` findings (SAT not in date on the record day, element older than the life limit).
- SAT → SCADA: in Do, "Fill furnace readings from SCADA" (`fillFromScada`) takes the PV of the thermocouple's column (`TC3` → `PV-3`) at the reading times (nearest row within half a step) from the loaded record, if it is linked to the cycle's furnace and chamber. The SAT API gives `statusAt(id, day)` and `elementAt(id, day)` for the SCADA page. Replacement records have an optional `time` for this.
- **Home page** (`renderHome` in `suite/shell.html`, a plain `<section>` in the shell, not a frame): overview of all furnaces from the SAT API `overview()` (per furnace/chamber: every active thermocouple's SAT status, element life, open cycles) and the SCADA API `overview()` (`last` = latest analysed record per `"F-0n|Chamber"`, kept by the SCADA page in `localStorage` `pfsr-last` via `lastSave`, never for example data; and the reviews with stage and overdue actions). Shows KPIs, one card per furnace with a status per chamber (crit = SAT due now, element overdue, overdue review action or an out-of-tolerance latest record without a closed review; warn = due soon, never tested, element due soon, open review), a chip per thermocouple, and a "Needs attention" list. Buttons use `HTQ.go("sat",{view})` and `HTQ.go("scada",{review})` (the SCADA page opens that review on `nav:scada`). With the quench API it adds a quench-tank block per furnace card (`HTQ.go("quench",{tank})` / `{test}`). It re-renders on the `sat:*` / `scada:*` / `quench:*` events.
- The shell owns the theme (`htq-theme`, applied to both frames; the SAT page hides its own Theme button in the suite), shows badges (SAT tab: thermocouples with SAT due now or element replacement overdue; SCADA tab: overdue review actions via the `scada` API `pdca()`), copies the page title for printing, and has a **Data** dialog that backs up / restores every suite key (`KEYS` in `suite/shell.html`; it also accepts the SAT page's own JSON export) and manages data **per tab** (`MODS` in `suite/shell.html`: each tab's keys and where its settings live): "Reset settings" removes the tab's settings (SCADA: the `pfsr-settings` key; the other pages: the `settings` field, plus `plan` for the quench page, inside their data key, which the page's `normalize` refills with defaults) and keeps the records; "Delete data…" removes all the tab's keys after the user types DELETE; both reload CALOR on that tab. It can also **clear all data** (removes every `KEYS` entry except the theme after the user types DELETE, then reloads). Both also empty what the standalone files see. When a page gets a new storage key, add it to `KEYS` and to its entry in `MODS`. Data is per browser: in Chrome/Edge all `file://` pages share one storage, so the suite sees what the standalone files saved. The SCADA page provides its API at the very end of its script (after everything it uses is defined). Each page prints itself (SCADA `IN_FRAME` is false in the suite, so its PDF button works).

## Process specifications: `Process_Specifications.html` (a CALOR tab)

Stand-alone single-file register of process specifications (recipes) per part and process, also embedded in CALOR (`/*@SPEC@*/`, first tab of the PROCESS group; badge = periodic reviews overdue (alert), else drafts awaiting approval). Same conventions as the quench page (its CSS and .xlsx writer were copied from it); `localStorage` `psr-reg` (data), `psr-view` (filter), `psr-theme` (standalone only); both data keys are in the CALOR `KEYS`.

- Processes `PROC`: `HT` hardening & tempering (CQI-9 Process Table A, quench included), `IA` isothermal annealing and `NORM` normalizing (Table E). Chamber roles `ROLE` follow the line: HT/IA austenitize in the hardening chamber (zone 1 preheats), then quench (HT) or controlled cooling (IA), then tempering / isothermal hold in the tempering chamber; normalizing preheats in the hardening chamber (700–750 °C) and austenitizes in the tempering chamber, fan cooling after exit optional. Full annealing (in the Production page's own list) is not offered here yet.
- A spec `{id PS-nnnn, rev, status draft|approved|obsolete, part, name, customer, drawing, grade, proc, furnaces[], pcs, wt, fixture, h[3], t[3], htol[3], ttol[3], push, pushTol, q{medium,tLo,tHi,delay(s),dip,transfer,agit}, cc{time,method,target}, nm{transfer,fan,fanTime}, req{hMin,hMax,scale,core,micro,decarb,grain,other,sample,method}, prep, revBy, appr, apprDate, change, notes, revs[], log}`; `fill()` completes it with the settings' defaults.
- `calc(s)`: time per zone = positions (`S.posH` 5,4,4 / `S.posT` 4,4,4; `normalize` corrects a saved 5,4,4 tempering layout once, flag `lay2`) × push; between chambers = `gapPos` × push + `gapMin`: quench delay + dip + transfer (HT, minutes), the controlled cooling cycle (IA: cooling time + `S.ccXfer` transfers, `gapPos` 0; `idle` = push − cycle; `advice` crit when the cycle does not fit in the push time, warn when < 1 min is left), transfer (NORM); `inForce()` gives `gapPos` / `gapMin`; time through the line; trays/pcs/kg per hour. `missing(s)` is the approval gate (incl. decarburization limit and sampling, and the reason for the change for rev > 0). `advice(s)` gives line-practice warnings (not CQI-9 requirements), duplicates per part + process, and in CALOR a mismatch with the furnace's quench tank medium.
- Document control: approved = locked; "New revision" pushes a snapshot to `revs` and starts a draft rev+1 while `eff(s)` (the revision in force) stays the last approved one; "Discard revision" restores it; "Make obsolete" needs a reason; only never-approved drafts can be deleted. `review(s)`: periodic review due `S.reviewDays` after the approval of the revision in force.
- Downloads: `specTables(s)` once → `specXlsx` (Specification, Thermal cycle, Revisions) and `specPdf` (controlled-document title block, approval block, revision history); `regXlsx` for the filtered register.
- CALOR API `spec`: `overview()` (in force, drafts, reviews due, specs in force per furnace) and `inForce()` (brief specs in force incl. `req`; used by the hardness page for the requirements, later also for SCADA set values / production). `nav:spec` takes `{spec}`. Home: a tile, a count per furnace card header, attention items for overdue reviews and drafts.
- Test with Playwright: click `#b-example`, edit via `#f-<path>` (dots → dashes) and `[data-f="h.1"]`, buttons `[data-d=save|approve|revise|discard|obsolete]`, read `window.__SPEC`.

## Start-up, shutdown and alarm response: `Furnace_Operations.html` (a CALOR tab, "Alarms")

Log of furnace start-ups, shutdowns and alarms with the response to each (CQI-9: start-up / shutdown / emergency procedures, alarm response, product in the furnace when the process is interrupted), also embedded in CALOR (`/*@OPS@*/`, PROCESS group after the SCADA review; badge = alarms active + reaction plans open). Same conventions (CSS and .xlsx writer copied from the quench page, assembled from a template with `/*@CSS@*/` and `/*@XLSX@*/`); `localStorage` `fop-reg`, `fop-view`, `fop-theme` (standalone); keys in `KEYS` and `MODS` (reset = settings, lists, alarms).

- Data `DB = {settings, lists{startup[], shutdown[]} ({k, t, crit}), alarms[] (the alarm response matrix: {k, name, cat, sev crit|major|minor, resp (min to acknowledge), stop (stops the line), imm, prod, notify}), events[], seq}`. Defaults `DEF_LISTS` / `DEF_ALARMS` are typical for a direct-fired gas pusher line with an oil quench, flagged to adapt to the furnace manual and the site's safety rules (response times are site targets, not CQI-9 figures).
- An event `{id OP-nnnn, kind startup|shutdown|alarm, furnace, area (AREAS), zone, type (SU_TYPES / SD_TYPES), reason, alarm (matrix key), start, ack, end, ready, firstPush, lastTray, value, done, affected yes|no|unknown, product, emptied, left, cl{key: ok|nok|na}, cln{key: note}, first{ref, res}, by, check{by, date, remarks}, act{contain, disp (DISP), verify, cause, action, owner, date}, closed, log}`; times are `datetime-local` strings without a time zone (`ms()` = UTC-naive, like the SCADA and production pages).
- `calc(e)`: start-up: checklist items not OK, soak between "all zones within tolerance" and the first tray vs `S.soakMin` (short soak = crit, product at risk first tray → ready + soak), first-off hardness (CALOR: `metal.testsBetween(f, firstPush, +S.firstHrs)`, else the typed `first`), pyrometry at start-up (SAT overview / TUS `statusAt`, one line per chamber), a hint to record maintenance/rebuild changes on the Equipment page; shutdown: product left inside; alarm: response time vs the matrix (late; not acknowledged in time while active = crit), duration, repeats (`S.repeatN` in `S.repeatDays` per furnace and type). `need` = reaction plan required (alarm: product affected / not known, late or repeating; start-up/shutdown: a crit finding). `missingRec` = record completeness, `missingAct` = reaction plan gate (containment and disposition when product is at risk, the releasing hardness check for "released after …", cause, action, owner, date), `canClose` adds the review / verification. `status`: active | react | incomplete | review | done | closed. `stateOf(f)`: running / stopped / stopped by a line-stopping alarm from the latest start-up, shutdown or `stop` alarm.
- `batchesIn(e, from, to)` (CALOR): batches of the production page in the area / zone during the window at risk (quench = trays leaving hardening zone 3). Downloads: `recTables(e)` → `recXlsx` / `recPdf`; `regXlsx` (Records, Alarm frequency, Alarm matrix, Checklists).
- CALOR API `ops`: `runPeriods(f, ch, t0, t1)` (last start-up in a SCADA record and the first shutdown / line-stopping alarm after it), `alarmsIn(f, ch, t0, t1)`, `used(f)`, `overview()` (`furnaces` with state, `items` needing action), `counts()`; `nav:ops` takes `{rec}` or `{view:{f}}`. The SCADA review uses it (`/* link to the start-up, shutdown and alarm log */`): `opsRun` fills `RUN` when its own start / stop inputs are empty (note `#runSrc`), `opsObs` lists the alarm records in the record and warns about excursions affecting trays with no alarm record once the log is in use for that furnace (tag "Alarm response", owner Production Manager). Home: a tile, a line per furnace card (state, alarms active, reactions open), attention items.
- Test with Playwright: click `#b-example`, `#b-alarm` / `#b-start` / `#b-stop`, edit `#f-<path>` (dots → dashes), "Now" buttons `[data-now=field]`, checklist `[data-cl=key]` / `[data-d=allok]`, buttons `[data-d=save|close-r|reopen]`, read `window.__OPS`.

## Control plan and PFMEA: `Control_Plan_PFMEA.html` (a CALOR tab, "CP & PFMEA")

Process FMEA per process family and control plan per part (IATF 16949 / CQI-9), also embedded in CALOR (`/*@CPF@*/`, QUALITY group; badge = PFMEA actions past their target date). Same conventions (CSS and .xlsx writer copied from the quench page); `localStorage` `cpf-reg`, `cpf-view`, `cpf-theme` (standalone); keys in `KEYS` and `MODS`.

- Data `DB = {settings, docs[], seq{pf, cp}}`; a doc `{id PF-nnnn | CP-nnnn, kind "pfmea"|"cp", title, proc HT|IA|NORM, (cp:) part, partName, customer, specId, specRef, pfmea, phase, keyContact, team, steps[{no, name}] (defaults `STEPS[proc]`, 10–80), rows[], rev, status draft|approved|obsolete, prep, appr, apprDate, change, notes, revs[], log, rseq}` with the same document control as the specifications (approve gate `missing`, new revision / discard / obsolete, periodic review `S.reviewDays`).
- **PFMEA = AIAG & VDA FMEA Handbook, 1st edition 2019 (the current edition), 7 steps.** Step 1 (planning and preparation) is the header of a PFMEA doc: `company, location, customer, program, subject, startDate, resp, conf (CONF), item, intent, timing, tasks, tools` plus `team` (revision date = last log entry). Steps 2–6 are the rows `{step, we, m4 (M4: Man/Machine/Material/EnvironMent/Method/Measurement), fItem, fStep, fWe, fe (effect on your plant / ship-to plant / end user), s, cls CC|SC, mode, cause, pc, o, dc, d, filter, pa, da, resp, target, status (ASTAT: Open … Completed / Not implemented), taken, doneDate, s2, o2, d2, cls2, remarks}`; step 7 = `results(d)` (AP before/after, action status counts). `normalize` migrates the old row fields (`func, effect, prev, det, act, owner, due, done` → `fStep, fe, pc, dc, pa, resp, target, taken`; function `mig`, also on `revs`). `ap(s,o,d)` = Action Priority H/M/L from the handbook logic, `CRIT` = abbreviated S/O/D criteria for the selects; both flagged "verify against your copy". **No RPN** (the handbook replaced it with AP). Helpers `apNow`, `apAfter` (re-rating of a Completed action), `openH`, `lateA`, `hasAct`, `closedA`. `pfRows(proc)` = default failure chains of a direct-fired pusher line (team to review and rate). Approval (`missing`) needs the step-1 essentials (item, subject, start date, responsibility), work element and 4M, step function, FE/FM/FC, PC/DC and S/O/D on every row; every AP-High row needs an action with responsible and target date (or "Not implemented" with remarks); a Completed action needs evidence, date and re-rated O/D. The dialog table (`pfTable`, class `pfm`) scrolls sideways under group headers 2–6; the PDF prints it as two tables (steps 2–5, then step 6).
- Control plan rows `{step, machine, prod, proc, cls, spec, tech, size, freq, ctrl, react, rec}` (`rec` = the CALOR page holding the records). `cpRows(spec)` generates them from the specification in force (spec API `inForce()`, which now also gives `q`, `pushTol`, `nm`, `ccM`, `customer`, `drawing`): receiving, loading, zone set values ± tol, push time, SAT, TUS, quench / controlled cooling / transfer / fan cooling, hardness, core, decarburization, microstructure, grain, dispatch. `markSpecial` carries the PFMEA's CC/SC steps onto the process characteristics; "Regenerate rows" re-reads the specification.
- `issues(d)`: periodic review; PFMEA: AP-High rows without a completed action, actions past target date, failures since the approval date (hardness `metal.ncSince(date, proc)`, `quench.failsSince`, `tus.failsSince`, `sat.failsSince`), no control plan referring to it; control plan: specification no longer in force or a newer revision in force, linked PFMEA missing / not approved, PFMEA steps without a control plan row, PFMEA special characteristics not marked in the control plan.
- Downloads: `docTables(d)` → `docXlsx` / `docPdf` (A4 landscape form). CALOR API `cpf`: `overview()` (docs with issues, AP-High open, late actions); `nav:cpf` takes `{doc}`. Home: a tile and attention items (late actions, document issues).
- Test with Playwright: click `#b-example`, `#b-newpf` / `#b-newcp` (dialog `#n-proc`, `#n-spec`, `#n-pf`, `[data-n=pfmea|cp]`), open `[data-open]`, edit a row `[data-row]` (row dialog `#r-<field>`, `[data-rr=ok]`), read `window.__CPF`.

## Equipment qualification: `Equipment_Qualification.html` (a CALOR tab, "Equipment")

Furnace / equipment survey and qualification record per chamber (CQI-9 pyrometry), also embedded in CALOR (`/*@EQUIP@*/`, last tab of the PYROMETRY group; badge = chambers not qualified). Same conventions (CSS and .xlsx writer copied from the quench page); `localStorage` `eqq-reg` (data), `eqq-view`, `eqq-theme` (standalone); keys in `KEYS` and `MODS` (reset = settings, classes, types). In CALOR a record is created for every furnace of the SAT register × Hardening / Tempering (`ensureRecs`).

- Data `DB = {settings, classes[{c, tol}], types[{t, rec, ind, load, otpInd, otp, sat, tus}], recs[], cseq}`. Classes 1–6 (±3 … ±28 °C) and instrumentation types A–E (needs + SAT / TUS intervals) are editable defaults flagged "confirm against the controlled CQI-9 copy". A record `{id "F-0n|Chamber", furnace, chamber, kind, heating, atm (ATM), zones, pos, burners, work, ctrlTc, control, rec (REC), recInt, otp (OTP), otpSensor, otpTest, load (LOAD), ctrlCal, recCal, instType, notes, prep, appr, apprDate, gaps{key:{action, owner, due, done}}, changes[{id CH-nnnn, date, kind, what, tus, sat, closed, ref}], log}` is the equipment survey record.
- `capability(r)`: the most demanding type the installed equipment supports (recording, independent recording, production load TCs, independent / any over-temperature protection) — the assigned type must not exceed it (honest assignment). `achieved(r)` = class of the loosest tolerance among the chamber's qualified TUS ranges (TUS API); `required(r)` = class of the tightest set-value tolerance (`htol`/`ttol`) of the specifications in force for the furnace (spec API).
- `checklist(r)` → items `ok|warn|crit|na` and level (`good` Qualified / `warn` with conditions / `crit` Not qualified): record approved and reviewed; type assigned and supported; TUS ranges (plus range interval vs the type's TUS interval); class achieved vs required; SAT of the chamber's control TCs and element life (SAT API, `satInterval` vs the type's SAT interval); controller and recorder calibration; over-temperature protection present / tested within `S.otpDays`; quench tank tests (hardening chamber, quench API); no change waiting for requalification; gaps. `gapsOf(r)`: honest gaps from the survey (over-temperature protection not independent / missing, recording on the control TCs / none, open furnace → decarburization check, no production load TCs, type not supported) with an editable action / owner / due / closed per gap.
- Changes: each needs a TUS and / or SAT after its date; `reqCheck` verifies it in CALOR (TUS API `lastPass(f, ch)`, every TC of the chamber with a non-failed SAT on/after the date); standalone it asks for a reference. Downloads: `eqTables(r)` → `eqXlsx` / `eqPdf` (equipment qualification record).
- CALOR API `equip`: `overview()` (per chamber: level, label, type, class, notMet, check, openChanges) and `counts()`; `nav:equip` takes `{view:{f,ch}}` or `{rec}`. Home: an "Equipment" line per chamber, a "Chambers qualified" tile, attention items only for items no other page reports (`EQOWN` in the shell). The page re-renders on `sat:*`, `tus:*`, `spec:*`, `quench:*`. The SAT API overview now also gives `satInterval`; the TUS API gives `lastPass` and each range's `interval`.
- Test with Playwright: click `#b-example`, open `[data-open="F-01|Hardening"]`, edit `#f-<field>`, gaps `[data-g="key.field"]`, record a change `[data-d=addch]` / close `[data-d="closech:i"]`, read `window.__EQ`.

## Temperature uniformity survey: `Temperature_Uniformity_Survey.html` (a CALOR tab, "Uniformity (TUS)")

Stand-alone single-file TUS register (CQI-9 pyrometry), also embedded in CALOR (`/*@TUS@*/`, tab "TUS" in the PYROMETRY group after the SAT; badge = ranges overdue + ranges whose last survey failed). Same conventions as the quench page (CSS and .xlsx writer copied from it); `localStorage` `tus-reg` (data), `tus-view` (furnace/chamber filter), `tus-theme` (standalone only); keys in the CALOR `KEYS` and `MODS`.

- Data `DB = {settings, ranges[], surveys[], seq, rseq}`. A **qualified range** `{id R-nn, furnace, chamber, lo, hi, tol, interval, note}` per chamber (defaults per furnace: hardening 700–960 °C, tempering 500–900 °C, ±10 °C, 365 d — multi-role chambers are qualified over their whole span; flagged in the page to confirm against CQI-9 / furnace class). A **survey** `{id TUS-nnnn, furnace, chamber, sp, kind, method, date, start, step, instr, instrCal, tcCert, tcCal, by, stab, tcs[{tag, loc, corr}], rd[[…]] (readings × TCs, as read), notes, check, act{cause,action,impact,by,date}, closed, log}`; readings can be pasted from Excel / a data-logger export (a leading time column is skipped).
- `calc(t)`: corrected readings (reading + TC correction) from reading `stab` on are judged against `sp ± tol` (tol of the range covering `sp`, `rangeFor`, else `S.tol`): `fail` beyond, `warn` beyond `S.warnPct` % of tol or with notes (fewer than `S.minTc` TCs, a TC without readings, no range covering `sp`); `invalid` when the instrument or the TUS TCs were out of calibration on the survey day. Per-TC min/max/mean, hottest/coldest, spread, overshoot before stabilisation.
- `rangeState(r, day)`: a survey counts for a range end when `|sp − end| ≤ S.endTol`; `fail` if the latest survey at an end failed, `none`/`partial` without passing surveys at both ends, else due = older passing end survey + interval (`ok` / `soon` / `overdue`). ## Separate tool: `Thermocouple_SAT_PDCA.html`

A stand-alone register that runs thermocouple System Accuracy Tests (CQI-9 SAT) through a Plan → Do → Check → Act cycle. It is **separate code from the SCADA review** (they only meet through the suite bridge): no shared code, no shared `localStorage` keys (it uses `tsat-pdca` for data, `tsat-theme` and `tsat-view`), no CDN scripts. Same single-file, no-build convention and the same colour tokens.

- Data `DB = {settings, sensors[], cycles[], seq}`; each cycle is one SAT `{id, sensor, stage, parent, plan, do, check, act, log}` with `stage` in `plan|do|check|act|closed`. `parent` links a re-SAT to the failed SAT.
- Do records `S.nRead` (default 30) timed pairs `do.readings = [{f, t}]`, one every `S.step` min from `do.start`, typed or pasted as two columns from Excel, with an optional timer that marks the reading due. Older records with single `do.furnace`/`do.test` are read by `readings(c)` as one pair.
- `calc(c)`: SAT difference = mean over the readings of furnace − (test + test instrument correction + test TC correction); `fail` beyond ±`tol`, `warn` beyond `warnPct` % of `tol`; any individual reading outside ±`tol` turns a pass into `warn`; a furnace range above `S.stab` is flagged. It also returns min/max/SD and the per-reading list for the Check chart. A test is invalid if the test instrument calibration had expired on the test day or the furnace was not stable (Check sends it back to Do).
- `missing(c)` is the stage gate used by `advance(c)`. A failed SAT closes only with root cause, action, product-impact assessment and a closed, passing re-SAT. A warning-band SAT needs a preventive action. Act can set a per-thermocouple interval, which `schedule()` uses for the next due date (last passing SAT + interval).
- **Furnaces and chambers:** `DB.furnaces` (default F-01 … F-04); every sensor has `furnace`, `chamber` (`Hardening` | `Tempering`), `tag` (shown, e.g. TC1), `serial`, `installed`. Tags default to `TC-01` … (`tcTag`); older `TC1`/`TC-1` tags are renamed in `normalize`; matching with the SCADA columns is by number (`tcNo`), and the register warns when the position breaks the odd = right / even = left rule (`wallClash`); `normalize` (v3) swaps saved positions that still carry the earlier wrong default. All thermocouples are type K (`TC_TYPE`): the type is not editable and `normalize` forces it on sensors and replacement records. Sensor `id` is internal and fixed (`F-01-H-TC1`); display with `sName`/`sLabel`, never the raw id. Records saved before v2 are migrated in `normalize` (old sensors → F-01 Hardening, default six TCs added for every other furnace/chamber). The furnace overview doubles as a page filter (`VIEW`, per viewer in `localStorage` `tsat-view`); every section and the print use `inView`/`cInView`.
- **Replacement history** `DB.repl = [{id TR-nnnn, sensor, date, oldSerial, oldInstalled, newSerial, newType, cert, reason, satRef, by, notes}]`. Saving updates the sensor's installed element (`syncSensor`). `verifySat(r)` = first valid SAT on/after the replacement date other than `satRef`; until it exists `schedule()` reports status `repl` (SAT due). An Act with action "Replace control thermocouple" cannot close without a replacement record whose `satRef` is that SAT.
- **Replacement cases** are `REASONS` (CQI-9 pyrometry cases: SAT failure, annual service life, drift, damage, open circuit, temperature/atmosphere exposure, TUS failure, wrong type/untraceable, relocation, other); old reason names are mapped in `normalize` via `OLD_REASONS`. Every record needs `offset` (controller offset reset); reason `R_MOVE` also needs a `tus` decision.
- **Annual replacement:** `lifeOf(sensor)` = install date + `S.lifeDays` (365), `over`/`soon` (within `S.lifeSoon`)/`ok`/`unknown`; shown in the schedule, furnace tiles, a KPI and the "Due for replacement" list (`drawDue`).
- **Test thermocouple validity:** Plan needs `plan.testTcCalDue`; `calc` makes a SAT invalid if that date is before the test, if `|do.tcCorr|` > `S.tcCorrMax` or if `plan.testTcUses` ≥ `S.testUsesMax` (0 = off). These limits are user settings to be confirmed against the controlled CQI-9 copy.
- **Download of a SAT cycle** (records-table row, the "Download a SAT cycle" picker `#dl-bar` for any cycle incl. Plan/Do, and the cycle window): `satTables(c)` builds the content once (summary, Plan, Do with all readings, Check with the statistics and validity findings, Act with product at risk and linked replacements, history). `satXlsx` writes a real .xlsx with the page's own minimal writer (`xlsxBlob` + stored-zip `zipBlob`, inline strings; the SAT page loads no libraries), `satPdf` opens a print-ready A4 document with the readings chart (Save as PDF). File names are plain ASCII (`dlName`): Chrome ignores a download name containing characters such as "·". The element tested is the removed element when the SAT led to a replacement.
- Product at risk for a failure is a date window since the last passing SAT (`riskWindow`), in line with the time-window approach of the SCADA app.

## Architecture of `Pusher_Furnace_SCADA_Review.html`

Sections are marked by `/* ---------- name ---------- */` banners. Flow: `parseAOA` → `analyze(D)` → `observations(D,A)` → `render(D,A,O)` (`run()` chains them and is re-run on every setting change). `analyze` returns `A`, also exposed as `window.__A`.

- **Rows** are `{t, pv, raw, sp, ev, tr, off}`. `t` is a UTC-naive clock time in ms (no time zone anywhere, including the `datetime-local` inputs via `parseLocal`). `pv` has values outside 500–1000 °C replaced by `null`; `raw` keeps the original for the integrity checks; set values outside 500–1000 are also `null`.
- **`ev` is the value that is judged.** It is `pv` except `null` while the furnace is off (optional start/stop inputs `RUN`) or settling after a set-value change or furnace start (per-thermocouple, until back within tolerance for `S.hold` readings, capped at `S.settle` min). All evaluation (tolerance, excursions, statistics, heat map, Pareto, wall difference) must use `ev`; `pv` is for plotting and data-integrity counts.
- **Deviation is always `PV − the row's own SET`** (`r.sp[k]??tc.sp`), never against one fixed setpoint, because the set value changes during a day. Statistics (`statistics`/`statEntry`) are computed separately per set value (`A.stats.groups`), each with its own limits.
- **Process rules** come from the chart heading (`detectFurnace` → `FTYPE`: `hardening` or `tempering`, accepting the misspelling "TEMPRING") and the set value in force (`procAt`, `affects`, `ignoreWhy`; threshold `HI_SET` = 800 °C). Hardening furnace: set > 800 counts every zone except Zone 1 (preheat zone), set ≤ 800 counts no trays; tempering furnace: all zones always count. Variation is always reported; only whether an excursion *affects trays* (`event.aff`) changes, which drives the verdict, the "Product affected: time windows" table (`A.windows`) and the management summary.
- **The push interval was removed on purpose.** Affected product is expressed as time windows plus the zone's tray positions, never as tray counts or charge/discharge times. Don't reintroduce push-time maths.
- **Settings** live in `DEF`/`S` (persisted in `localStorage` key `pfsr-settings`); each key needs an `<input id="key">`. Other `localStorage` keys: `pfsr-repl` (thermocouple replacement register) and `pfsr-hist` (one summary per furnace and day, so replacements made between two exports can be judged by comparing days before and after; example data is never saved).
- **Review PDCA** (`/* review PDCA */` section, `localStorage` `pfsr-pdca`; reviews of the example record stay in memory, `PD_MEM`): one review per record (`recKey` = furnace key + first/last day). `pdItems` turns the priority list (`A.priority`, Pareto order with owners) plus findings it does not cover (`TAGOWN` tags: SAT, thermocouple life, replacement, set change, uniformity) into suggested actions. The reviewer decides each one in Plan (adopt / change / no action with a reason; P0 product containment cannot be skipped), records Do (date, what was done, product disposition `DISPO`), Check (effective or not, evidence; `pdEvidence` suggests it from later days of the same furnace in `HIST`) and Act (documents standardised `DOCS`, approver). `pdMissing` is the stage gate. Not-effective actions go back to Plan in a new cycle (`pdReplan`, earlier attempt kept in `item.hist`, other actions locked). The interactive panel `#pdcaPanel` sits outside `#out` (so report reruns don't drop focus); `pdPrint` puts the reaction plan into the printed report. The record key is per furnace **and chamber**: `furnaceKey(D)` = `furnaceBase(D)` + the chamber from `detectFurnace` (e.g. `FURNACE-4 HARDENING`), so the hardening and tempering exports of the same furnace and day get separate reviews, history (`pfsr-hist`) and links. Data saved before that ("FURNACE-4") is migrated on load: reviews and `LAST` fkeys get the chamber from the saved heading / link; old history entries match either chamber (`histOf`); an old `pfsr-link` override applies only to the chamber it names. Reviews are only created by "Start review (Plan)" on a loaded non-example record; each register row can also be deleted (with confirmation, any stage). Any review can be downloaded from the review register (Excel / PDF per row) or from the open review: `pdTables` builds the content once (summary, Plan, Do, Check, Act, earlier cycles, history), `pdXlsx` writes a workbook with SheetJS, `pdPdf` opens an A4 landscape document and the print dialog. `pdReplan` keeps each finished cycle's sign-offs and dates in `R.past`. A review can be downloaded from its panel: `pdTables(R)` builds the content once (summary, Plan, Do, Check, Act incl. no-action reasons and earlier not-effective cycles, history); `pdXlsx` writes it with SheetJS as sheets Summary/Plan/Do/Check/Act/History, `pdPdf` opens it as a print-ready A4 landscape document in a new window (Save as PDF).
- **Link to the production report (CALOR only)** (`/* link to the production report */`): `prodTrace(D,A)` (run in `run()` as `A.prod`, before `observations`) takes the batches of the linked furnace from `HTQ.api("prod").reports()` whose zone windows in the linked chamber overlap the record; a batch is affected (`b.wins`) when its window in a zone overlaps an affected incident of that zone (`e.aff`, `e.winFrom`–`e.winTo`). For each batch and zone it collects the SCADA set values (`r.sp` of the zone's two TCs) while the batch was in the zone and compares them with the batch's specification (`h` or `t` by chamber): `ok` / `diff` / `nospec` / `nodata`. `prodPriority` names the held batches in the P0 rows of the priority list (and so in the review's suggested actions); `prodObs` adds a "Specification" finding (set values differ; owner HT Manager in `TAGOWN`) and info findings for a day without a production report or batches without complete times; `traceTable` gets a "Batches" column and `prodSection` lists every batch. The page re-runs on `prod:ready` / `prod:changed` / `spec:changed`. This uses the production page's recorded entry/exit per batch, not push maths in the SCADA review.
- **Tray positions** per zone come from the chamber: `traysIn(z)` uses `trays1..3` (hardening 5/4/4) or `ttrays1..3` (tempering 4/4/4) by `FTYPE`.
- **Wall layout:** use `isLeft(k)` / `wallOf(k)` / `wallCol(k)` (index `k` = TC number − 1, so `k` odd is the left wall), never `k%2` directly. Zones are `{L: z*2+1, R: z*2}` (L = left-wall TC); wall difference = left − right; colour `--s1` = left, `--s2` = right.
- **Management summary** (`mgmtSection`) is role-based (Director, Maintenance Head, Production Manager, HT Manager, Quality Manager); the owners in `pareto`/`priorityList` use the same role names.
- **Charts:** zone trend charts are Chart.js (`drawCharts`, with a plugin that shades off/settling periods); everything else is hand-built SVG strings. Chart scales are clamped to 500–1000 °C. Printing goes through `enterPrint`/`exitPrint`, which re-runs `run()` with `PRINTING` set; `.noprint` elements are hidden by the print CSS.

## Domain conventions to keep

- Valid and plotted temperature range is 500–1000 °C; anything outside is excluded and reported, never drawn.
- Default tolerance ±10 °C (CQI-9 furnace-class selector from the older apps was dropped here). An exact 800 °C set value is treated as the lower class (preheating/tempering).
- A thermocouple that reads 0 for the whole file is "offline" and is shown as such, not as zero data.
- **"N/A" means "Not available"** (also "NA", "not available"; `isNA` in the production, specification and hardness pages). It counts as an entry (the field is not missing) but is never an identity: no duplicate / clash matches on it (production batch and heat checks, specification duplicates per part), no heat of its own in the totals ("Heat no. not available"), no automatic re-test match in the hardness page (`idKey`: batch, else heat no., else heat code; otherwise the reaction plan names the re-test record, `act.retest`). Apply the same rule to any new matching or grouping on entered text.
